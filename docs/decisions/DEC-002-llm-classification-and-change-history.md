# DEC-002: LLM 자동 분류·탐색 메뉴와 문서 변경 이력

## 상태

Proposed — Dev Wiki의 **최종 목표**로 확정. 단계적으로 구현합니다.

## 배경

[DEC-001](./DEC-001-docusaurus-wiki.md)로 Docusaurus 위키를 세우고,
그 위에 제출 → 분류 → 승인 → 발행 파이프라인을 붙였습니다. 파이프라인은
끝까지 동작하지만, "LLM Wiki"라는 이름의 핵심 두 가지가 비어 있습니다.

1. **분류가 LLM이 아닙니다.** `classifier.mjs`의 `categoryRules`는 제목과
   본문에서 키워드를 찾아 다섯 카테고리에 매핑하는 규칙일 뿐입니다.
2. **메뉴가 자동이 아닙니다.** `sidebars.ts`는 문서 경로를 사람이 손으로
   나열한 파일입니다. 발행해도 메뉴에 나타나지 않아, 문서가 늘수록
   실제 위키 내용과 탐색 구조가 어긋납니다.

동시에 **누가 무엇을 언제 넣고 바꿨는지**가 문서를 읽는 자리에서
보이지 않습니다. 감사 기록은 `llm_wiki/log.md`와 DB `review_events`에만
있어, 위키 독자는 지금 읽는 문서가 언제 누구 손에 어떻게 바뀌었는지
알 수 없습니다.

## 결정

다음 네 가지를 Dev Wiki의 최종 목표로 삼습니다.

### 1. 카테고리를 LLM이 분류한다

키워드 규칙을 실제 LLM 호출로 교체합니다. `llm_wiki/schema.md`를
프롬프트 컨텍스트로 넣어, 카테고리 정의와 처리 규칙을 모델이 근거로
쓰게 합니다. LLM은 카테고리 하나만 고르는 것이 아니라 다음을 함께
결정합니다.

| 출력 | 용도 |
| --- | --- |
| `category` | 발행 경로 결정 (development / operations / standards / decisions / knowledge) |
| `tags` | 주제 태그. 교차 탐색의 기준 |
| `title`, `summary` | 독자가 목록에서 읽을 제목과 한 줄 요약 |
| `reasoning` | 왜 이 카테고리인지. 문서의 「분류 결과」에 남김 |
| `confidence` | 낮으면 자동 발행 대신 사람 확인을 요청 |
| `related` | 기존 문서 중 함께 읽을 후보 |
| `menu` | 메뉴에서의 위치와 순서 제안 (아래 2번) |

**사람의 승인 단계는 유지합니다.** LLM은 초안까지만 만들고, `docs/`
발행은 reviewer/admin 승인 뒤에만 일어납니다. 자동화의 대상은 분류이지
발행 권한이 아닙니다.

### 2. 메뉴를 분류 결과에서 자동으로 만든다

`sidebars.ts` 수기 관리를 끝냅니다. 발행된 문서와 LLM 분류 결과로부터
사이드바를 생성해, 발행 즉시 메뉴에 반영되게 합니다.

메뉴의 목표는 단순 나열이 아니라 **독자가 차근차근 좁혀 들어가며 조사할
수 있는 구조**입니다.

- **개요에서 세부로.** 각 카테고리는 개요 문서를 먼저 두고, 그 아래
  세부 문서를 배치합니다. 처음 온 사람이 위에서부터 읽어 내려가면
  맥락이 쌓이도록 순서를 정합니다.
- **주제 묶음.** 문서가 많아지면 LLM이 태그를 근거로 하위 그룹을
  제안합니다. 예를 들어 운영 문서 아래 「배포」, 「장애 대응」,
  「모니터링」.
- **다음에 읽을 문서.** 각 문서 끝에 관련 문서 링크를 두어, 메뉴를
  벗어나지 않고도 추적 조사가 이어지게 합니다.
- **난이도·선행 문서 표시.** 선행 지식이 필요한 문서는 먼저 읽을
  문서를 가리킵니다.

메뉴 구조는 생성물이되 **사람이 덮어쓸 수 있어야 합니다.** LLM 제안을
그대로 쓰는 것이 기본값이고, 고정하고 싶은 순서나 라벨은 별도 설정에
적어 생성 결과보다 우선하게 합니다.

### 3. 로그인한 사용자의 모든 기여를 기록한다

모든 사용자는 로그인 후에만 제출·수정·승인할 수 있고, 모든 행위는
**누가, 언제, 무엇을, 어떻게** 형태로 남습니다.

| 시점 | 기록할 것 |
| --- | --- |
| 제출 | 제출자, 시각, 원본 파일, 제목, 본문 |
| 분류 | 사용한 모델, 결과 카테고리, 근거, 확신도 |
| 수정 | 수정자, 시각, 바뀐 내용, 바뀌기 전 내용 |
| 승인·거절 | 심사자, 시각, 메모, 발행 경로 |
| 롤백 | 사유와 되돌린 지점 |

기록은 세 곳에 남습니다. DB(`submissions`, `review_events`, 신설
`document_revisions`)는 조회용, `llm_wiki/log.md`는 추적용 감사 로그,
그리고 **문서 본문 끝의 변경 이력**은 독자용입니다.

### 4. 모든 문서 끝에 변경 이력을 남긴다

발행되는 모든 문서는 마지막에 `## 변경 이력` 섹션을 가집니다. 독자가
문서를 읽은 자리에서 바로 출처와 변경 과정을 확인할 수 있어야 합니다.

```md
## 변경 이력

| 버전 | 일시 | 기록자 | 변경 내용 | 이전 기록 |
| --- | --- | --- | --- | --- |
| v3 | 2026-09-21 14:02 | 김개발 | 롤백 절차에 DB 스냅샷 단계 추가 | [v2](../../llm_wiki/revisions/<id>/v2.md) |
| v2 | 2026-09-04 09:31 | 이운영 | 포트 번호 3000 으로 정정 | [v1](../../llm_wiki/revisions/<id>/v1.md) |
| v1 | 2026-08-17 22:56 | 박제출 | 최초 발행 (LLM 분류: operations, 확신도 0.86) | — |
```

규칙은 다음과 같습니다.

- **새로 쓰지 않고 덧붙입니다.** 갱신할 때마다 맨 위에 새 줄을 추가하고
  기존 줄은 지우지 않습니다.
- **이전 기록을 참조할 수 있어야 합니다.** 각 버전은 그 시점의 본문
  전문을 가리킵니다. 개정본은 원본과 마찬가지로 불변 보관합니다.
- **변경 내용은 사람이 읽을 문장으로 적습니다.** diff 덩어리가 아니라
  무엇이 왜 바뀌었는지 한 줄로 요약하며, 요약은 LLM이 제안하고
  기록자가 고칠 수 있습니다.
- **기록자는 로그인 계정입니다.** 표시 이름을 적고 이메일은 적지
  않습니다.
- **재승인은 같은 경로를 덮어쓰고 버전을 올립니다.** 지금처럼 접미사를
  붙인 중복 파일을 만들지 않습니다.

## 이유

- 위키가 실패하는 가장 큰 이유는 아무도 문서를 쓰지 않는 것입니다.
  분류와 메뉴 배치라는 **정리 노동을 기계가 가져가면** 기여 문턱이
  낮아집니다.
- 문서가 늘어날수록 탐색 구조가 가치를 정합니다. 손으로 관리하는
  사이드바는 반드시 뒤처집니다.
- 변경 이력이 문서 안에 있으면 독자가 **신뢰도를 스스로 판단**할 수
  있습니다. 언제 마지막으로 손봤는지, 누가 책임지는지가 보입니다.
- 감사 기록은 사고가 났을 때가 아니라 평소에 쌓여 있어야 합니다.

## 구현 단계

순서대로 진행합니다. 각 단계는 그 자체로 쓸모가 있어야 합니다.

| 단계 | 내용 | 선행 조건 |
| --- | --- | --- |
| 1 | 재승인 시 같은 경로 덮어쓰기 + 버전 증가 (현재 P2 이슈) | — |
| 2 | `document_revisions` 테이블과 개정본 불변 보관 | 1 |
| 3 | 문서 끝 `## 변경 이력` 섹션 자동 생성·추가 | 2 |
| 4 | 분류기를 실제 LLM 호출로 교체, `schema.md`를 프롬프트에 주입 | — |
| 5 | 분류 결과에서 사이드바 생성, 수기 `sidebars.ts` 폐지 | 4 |
| 6 | 태그 기반 하위 그룹과 관련 문서·선행 문서 링크 | 5 |

## 주의할 점

- **승인 트랜잭션 순서를 깨지 마세요.** 복사 → 빌드 → 성공 시에만 DB
  확정 → 감사 로그입니다. 변경 이력 기록도 이 순서 안에 들어가야
  합니다. 빌드가 실패하면 이력도 함께 되돌아가야 합니다.
- **LLM 출력은 그대로 믿지 않습니다.** 카테고리는 정해진 다섯 개
  안에서만 받고, 경로는 서버가 만듭니다. 제목·요약은 프런트매터에
  넣기 전에 따옴표 처리합니다. 모델이 만든 문자열이 YAML을 깨면 위키
  빌드 전체가 죽습니다.
- **민감 정보는 초안에 넣지 않습니다.** 토큰, 비밀번호, 개인정보는
  분류 단계에서 걸러야 하며, 변경 이력에도 남기지 않습니다.
- **LLM 호출은 실패할 수 있습니다.** 호출이 실패하면 지금의 키워드
  규칙으로 물러나 `needs_reclassify` 상태로 두고, 사람이 다시 돌릴 수
  있게 합니다.

## 결과

이 목표가 달성되면 Dev Wiki는 다음 상태가 됩니다.

팀원은 글을 던지기만 하면 됩니다. LLM이 카테고리와 태그를 정하고 메뉴의
어느 자리에 놓을지까지 제안합니다. 담당자가 승인하면 문서가 발행되고
메뉴가 스스로 자랍니다. 위키를 찾은 사람은 개요에서 세부로 좁혀 들어가며
필요한 문서까지 도달하고, 문서 끝에서 이 내용을 누가 언제 왜 바꿨는지와
이전 판을 바로 확인합니다.
